# 短期错误诊断正文是 usage-owned 请求审计的窄例外

例外所针对的既有约束：usage-owned 请求审计只保存协议元数据与事件骨架（路由、允许记录的头、协议字段名与枚举、体量、内容指纹，以及真实存在的会话或请求标识），不保存模型正文（用户输入、模型输出、工具参数与结果、流式文本或增量），也不保存认证凭据原文或上游错误 message 原文。该约束连「默认关闭、排障时加密临时揭示」这一档也不选；理由是不让用户输入、模型输出和工具内容落库。

新的上游错误诊断要求管理员按需查看**真实发往上游**的失败请求 JSON，因此必须显式开一个**有范围**的例外，而不是悄悄放宽上述约束，也不能据此把正文塞回 usage-owned 请求审计。

例外范围：

- 只用于独立于 usage-owned 请求审计的短期诊断记录：仅在现有请求审计实际覆盖的 Messages／Chat Completions／Responses HTTP 分支、该次**真实上游尝试**收到 4xx/5xx 时采集（请求审计只在已有使用记录时写入，未覆盖的入口记作「未采集」）；未收到 HTTP 响应的连接故障、本地拒绝、仅 SSE 中途错误及 `phase1_uncovered` 分支不在内。
- 只保存实际发出且合格的完整文本 JSON（≤1 MiB、无附件／编码媒体、无已知结构化凭据，例如平台注入的认证头、Cookie、API Key、代理凭据、URL query 密钥，以及客户端在结构化字段提供的 `fallback_credit_token`）。认证凭据原文与上游错误 message 原文一律不落库；不合格正文不截断、不脱敏后仍称「完整」。
- 正文必须加密，不明文回退。正文 7 天、独立净化元数据 30 天；到期后 API **精确地在该时刻**立即拒绝读取（失效按创建时间即时计算，不受清理进度影响）。**在线主库**的密文／行由周期批处理物理清除（约 10 分钟一轮、每轮至多 500 行；进程停机期间不执行，恢复后补清），延迟**无硬性最大延迟，受积压与停机影响**，只能靠监控与告警暴露，因此不承诺到期即刻完成，也不承诺任何最大延迟数值。拒绝读取不等于删除，须以主库删除结果为准。**该项已由用户明确确认接受（“接受周期清理”）**。积压量与最老记录时长观测**已实现**：清理服务每轮调用 `observeBacklog`，上报 `error_diagnostic.cleanup_backlog` 事件（码 `cleanup_backlog`，字段 `bodies_overdue` / `records_overdue` / `oldest_overdue_seconds`）与超期 gauge（`OverdueBodies` / `OverdueRecords` / `OldestOverdueSeconds`），探针失败另有 `backlog_probe_failed` 告警。**范围与剩余风险**：积压观测是存储层的**可选**能力（`ErrorDiagnosticCleanupBacklogReader`），未提供时静默跳过（`Backlog()` 返回 `ErrErrorDiagnosticBacklogUnsupported`），那时没有积压可见性；gauge 是进程内最近一次观测值，进程重启后要到下一轮才有数据；积压只表示在线主库上的**物理残留**，不代表内容可读（API 在到期时刻已拒绝），也不构成任何延迟上限。
- 本例外**不承诺**备份、只读副本、PITR 或人工导出中不可恢复：这些存储中的旧数据是已声明的剩余风险。例外也**不是合规／隐私擦除**手段，不得用于满足删除请求或数据主体权利。
- 只有管理员能按需解密查看；获得账号查看能力的普通用户不能读取诊断正文或管理员请求审计。
- **默认关闭**：生产采集与正文留存默认关闭，由运维在完成书面风险确认（含自由文本可能含未知密钥、备份／副本／PITR 可能留存、非合规擦除）后显式开启。测试只用合成／本地数据。

## 429 头值：同一例外里的另一条窄路径

上游 **429** 的排障还需要**头值**（客户端希望看到 `Retry-After`、`Anthropic-Ratelimit-*` 的真实取值）。它与正文是两条独立路径，刻意不共用开关、不共用到期时刻、不互相代替：

- **范围更窄**：只对 **Claude Messages**（`/v1/messages`）的真实上游尝试、且该次尝试**恰好收到 HTTP 429** 时采集；其它协议与其它 4xx/5xx 一律记作「未采集」（`not_observed`）。「不在范围」是未采集，不是跳过，也不是失败。
- **独立开关**：`header_values_enabled`，与 `body_retention_enabled` 正交。正文关闭时头值照常采集，头值关闭时正文行为一字不改。风险确认（Enabled + RiskAcknowledged）仍是两者共同的前置门槛；生产默认关闭，需运维显式开启。书面确认的语句必须把这一层写进去（头值同为 **7 天**、只采白名单、绝不含 Cookie／Authorization 等凭据头），语句内容变化即提升版本：按只讲正文的旧语句做过的确认不再覆盖当前语句，因此已存量的部署会被判为「确认过期」，在重新逐字确认前不采集（门控既有语义，本次语句扩充即为一次实例）——**不因为库里已有一条旧确认就静默放行**，头值层也不会被正文开关顺带打开。开启该层与开启正文留存同门槛：本次逐字确认 + 可用稳定密钥（两者共用同一把）；机器凭证只能读与关。运维状态面同时给出**存量开关**与**校验后的结论**，让「存量开着但不生效」可见，且不把结论写回采集读取器（接缝仍需据存量开关表达「要求过、但拿不出密钥」）。
- **闭集名单 + 有界校验**：只接受白名单内的头名（`Host`、`User-Agent`、`Anthropic-Version`／`Beta`、`Accept*`、`Content-Type`、`X-Request-Id`／`X-Client-Request-Id`／`X-Claude-Code-Session-Id`、`X-Stainless-*`、`Retry-After`、`Anthropic-Ratelimit-{Requests,Input-Tokens,Output-Tokens}-{Limit,Remaining,Reset}`），取值按族校验（日期、媒体类型、无符号整数、RFC3339／HTTP-date、不透明 ID、主机名、有界文本）。**未列名的头名是有意排除**：一律不读入快照、不落库、不记名，也不构成「快照不完整」（名单就是信任边界，见「剩余风险」）。超界取值、含控制字符或含凭据形态（`Bearer `、`sk-`、`api_key`、`password`、`-----BEGIN` 等）的值一律拒绝。`Retry-After` 与 `Anthropic-Ratelimit-*-Reset` 按 RFC 9110 接受 HTTP-date 形态（上游确实会发），不做「只认秒数」的收窄——否则合法的 HTTP-date 会以「取值不合格」的形态把整份快照带走。
- **绝不保存凭据类头**：`Authorization`、`Cookie`、`Set-Cookie`、`X-Api-Key`、`Proxy-Authorization`、`WWW-Authenticate` 等只允许在净化器里做存在性判断，**存在性本身也不落库**；本能力只保存值。原始 `http.Header` 从不进入诊断记录。
- **整份或全无（针对有资格的头）**：这里的「整份」是**白名单内、有资格进快照的头**，不是原始 `http.Header` 的全部头名。一份快照要么整份落库，要么整份丢弃并留下稳定原因码（`skipped_invalid_values`）。不做静默截断——半份快照会被管理员读成「上游只发了这几个头」，比没有记录更危险。判定依据是净化器的**有资格省略摘要**（只含计数）：只要有**一个白名单内的头**没能进快照（取值没过取值族校验、超出行数／条目／字节预算），整份快照即判为不合格，此时一个取值都不交给服务层。两类排除**不计入省略**、也不会让快照作废：闭集外的头名（有意排除，`Date`／`Content-Length` 这类真实响应常见的头就在此列）与凭据类头的存在性标记（设计内排除）。因此普通 429（每个请求都带 `Authorization`／`Cookie`，每个响应都带 `Date`／`Content-Length`）仍然拿得到快照。
- **披露口径（管理端）**：管理端把这些快照标注为**「只含白名单内允许记录的头值」（allowlisted values only）**，不得表述为完整抓取上游 wire 头；快照本身也不断言「上游只发了这些头」——未列名头不在范围内，既不出现也不被声明为不存在。
- **上游形态也是范围条件**：`/v1/messages` 是入站路由，不等于真实上游形态。经该路由入站但真实上游不是 Claude Messages 的尝试（例如 Bedrock：请求头是 SigV4 形态、响应头是 `x-amzn-*` 形态）在头值这一层按**未采集**（`not_observed`）记录，而不是按 Claude Messages 的头值契约采集并留下「采集失败」的原因码——错误的协议标签比没有标签更危险。这一判定只影响头值：该次尝试的协议元数据与正文诊断照旧。
- **多行同名头**：同一头名多行时按 HTTP 的列表语义合并成一个以 `", "` 分隔的取值（RFC 9110：多个同名字段行等价于逗号分隔的列表），因此**不会丢掉除第一行之外的安全取值**；合并只对按列表取值的那一族头名成立，结构化取值的头名（不透明 ID、整数、日期、媒体类型、主机名）出现多行即整份不合格，绝不只是保留第一行。
- **加密与到期**：与正文共用同一把稳定密钥，密文入库、不明文回退；**7 天**到期（独立列，独立到期时刻），到期时刻由 API **精确拒绝读取**并如实披露（`header_expires_at`）。读接口禁止任何中间缓存（`no-store`）。在线主库的物理清除同样是约 10 分钟一轮、每轮至多 500 行的周期批处理，停机与积压会推迟它，因此不承诺确切删除时刻；积压观测已扩展到这一列（`header_values_overdue`），使「这一层是否落后」可被监控看见。
- **权限**：只有管理员能按需解密查看；获得账号查看能力的普通用户不能读取。揭示头值与揭示正文是两个独立动作，互不读取对方。
- **剩余风险（不得淡化）**：白名单之外的头名不采，值内的未知秘密无法被自动识别——名单是信任边界，不是「绝无秘密」的保证；备份、副本与 PITR 中的留存同样是已声明的剩余风险，本例外不是合规／隐私擦除手段，也不得用于满足删除请求或数据主体权利。

## Considered Options

- 修订既有审计约束，允许请求审计保留模型正文
- 保持既有审计约束不变，放弃错误请求正文诊断
- 不改既有审计约束，另建有范围、默认关闭、短期且权限隔离的独立例外

选第三项。既有约束对 usage-owned 请求审计的要求不变：审计仍只保存协议元数据与事件骨架，不保存模型正文、认证凭据原文或上游错误 message 原文；既有审计测试的禁止条款继续有效。429 头值是同一例外里的另一条窄路径（见上一节）：它既不把正文塞回请求审计，也没有把「已保存头值」扩大成「已保存正文」。
